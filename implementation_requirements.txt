SMART HOME APP - FULL IMPLEMENTATION REQUIREMENTS
==================================================

PROJECT GOAL:
Transform the current Flutter + Firebase app into a high-fidelity Smart Home
management system based on Figma screenshots, BUILT ON TOP OF the existing
backend architecture (data model, Firestore structure, sync logic, and Cloud
Functions) that is already implemented and working. Do NOT change the
Firestore schema or field names described in Section 0 unless explicitly
instructed — the UI should consume and display this existing data, not
redefine it.

0.3 FIRESTORE SCHEMA (DO NOT CHANGE FIELD NAMES)
/floors/{floorId}
    name: string
    gridWidth: number
    gridHeight: number
    imageUrl: string

/floors/{floorId}/devices/{deviceId}
    type: "outlet" | "multiswitch" | "iron" | "bulb" | "camera"
    name: string
    x: number
    y: number
    status: "ON" | "OFF" | "ERROR" | "DISCONNECTED"

    # multiswitch only
    switches: [ { id, label, state } ]

    # iron only (safety-critical)
    maxOnDurationMinutes: number
    turnedOnAt: timestamp | null

    # bulb only (scheduled)
    scheduleStart: string          # e.g. "18:00"
    scheduleEnd: string            # e.g. "23:00"

    # camera only
    snapshotUrl: string

/usageLogs/{logId}
    deviceId: string
    floorId: string
    event: "ON" | "OFF" | "AUTO_CUTOFF"
    timestamp: timestamp

/alerts/{alertId}
    deviceId: string
    message: string
    timestamp: timestamp
    acknowledged: boolean

0.4 DEVICE MODEL (lib/models/device.dart) — ALREADY IMPLEMENTED
* Abstract base class `Device` with fields: id, floorId, name, type, x, y, status
* `DeviceStatus` enum: on, off, error, disconnected (+ string conversion helpers)
* Subclasses (each with their own toMap() and fromFirestore parsing):
    - OutletDevice        (simple binary ON/OFF)
    - MultiSwitchDevice   (has `switches: List<SwitchItem>`, each with id/label/state)
    - IronDevice          (has maxOnDurationMinutes, turnedOnAt — safety-critical)
    - BulbDevice          (has scheduleStart, scheduleEnd)
    - CameraDevice        (has snapshotUrl)
* `Device.fromFirestore(floorId, doc)` factory picks the correct subclass based
  on the `type` field.

0.5 FIRESTORE SERVICE (lib/services/firestore_service.dart) — ALREADY IMPLEMENTED
Available methods the UI should call (do not duplicate this logic in widgets):
* streamFloors() -> Stream<QuerySnapshot>
* addFloor({name, gridWidth, gridHeight, imageUrl})
* deleteFloor(floorId)
* streamDevices(floorId) -> Stream<List<Device>>   (already parsed into typed objects)
* addDevice(floorId, Device)
* updateDeviceStatus(floorId, deviceId, DeviceStatus)
* toggleDevice(floorId, deviceId, bool turnOn)      (also stamps turnedOnAt, logs to usageLogs)
* toggleSubSwitch(floorId, deviceId, switches, switchId, newState)
* streamUsageLogs(deviceId) -> Stream<QuerySnapshot>
* streamAlerts() -> Stream<QuerySnapshot>

0.6 SYNCHRONIZATION MECHANISM — ALREADY WORKING
* All live UI is driven by Firestore `snapshots()` streams wrapped in
  StreamBuilder — NOT manual refresh/polling.
* Confirmed working bidirectionally: app writes reflect in Firebase Console
  instantly, and console/external writes reflect back into the app UI live.
* Any new UI screens MUST follow this same StreamBuilder + FirestoreService
  pattern rather than one-off fetches, to preserve real-time behavior.

0.7 SAFETY CUTOFF (Cloud Function) — WORKING, VERIFIED
* `functions/src/index.ts` exports `checkSafetyCutoffs`, an `onSchedule`
  function (runs every 1 minute in production).
* Logic: finds all devices with type "iron" and status "ON" across all
  floors; if `(now - turnedOnAt) > maxOnDurationMinutes`, force-sets
  status to "OFF", clears turnedOnAt, writes an "AUTO_CUTOFF" entry to
  usageLogs, and writes a message to /alerts.
* Verified locally via Firebase Emulator Suite (Functions + Firestore +
  Pub/Sub emulators running together); confirmed 200 OK execution.
* NOTE: uses the modular Admin SDK syntax (`initializeApp` from
  "firebase-admin/app", `getFirestore`/`FieldValue` from
  "firebase-admin/firestore") — do not revert to the namespaced
  `admin.firestore()` style, it caused emulator crashes.

0.8 CURRENT UI (BEING REPLACED / UPGRADED BY THIS SPEC)
* FloorsScreen: simple ListView of floors with a "+" FAB to add a floor,
  and a temporary seed-data button in the AppBar.
* FloorDetailScreen: simple ListView/Card list of devices on a floor,
  a toggle Switch for OutletDevice, "+" FAB to add an outlet.
* This is intentionally basic scaffolding — Section 1-3 below describe the
  full visual redesign to build on top of this working data layer.

0.9 STILL OUTSTANDING (not yet built, may overlap with UI work below)

2. SCREEN SPECIFICATIONS
==================================================

A. HOME SCREEN (DASHBOARD)
* Header:
    - Rounded User Profile Image.
    - Greeting ("Good morning, [Name]").
    - Icons: Calendar, Automation (Robot), Notifications (with Badge —
      badge count sourced from streamAlerts() where acknowledged == false).
* Status Bar: "X devices active" with a "Manage" chevron link.
    - X = count of devices across all floors where status == "ON"
      (aggregate via streamDevices per floor, or a new aggregate method
      added to FirestoreService if needed).
* Floor Selector: Horizontal scrollable chips, populated from
  streamFloors() (replaces/augments the current basic ListView in
  FloorsScreen).
* Quick Action Buttons: 3 Large cards (All Lights, Turn Off All, Lock House).
    - "All Lights" / "Turn Off All" should batch-call toggleDevice()
      across the relevant devices — consider adding a batch helper to
      FirestoreService rather than looping individual writes from the UI.
* Room Selector: Horizontal scrollable chips (Living Room, Kitchen,
  Bedroom). NOTE: current schema has no explicit "room" field on devices
  or floors — this needs either (a) a new `room` string field added to
  the device document, or (b) rooms modeled as a subdivision of a floor.
  Flag this as a schema addition, not a rename, to avoid breaking
  existing floor/device documents.
* Device Grid:
    - 2-column grid of cards, replacing the current basic Card/ListTile
      in FloorDetailScreen.
    - Each card: Icon (by type), Name, Sub-status (e.g., 100%, 4°C —
      NOTE: no existing field carries this; treat as optional/future
      metadata field per device type, do not block core toggle
      functionality on it), ON/OFF text (from `status`).
    - Power toggle button in top-right of the card, wired to
      toggleDevice() / toggleSubSwitch() as appropriate per device type.
* Room Details (Living Room):
    - Overlay/Panel for "Smart TV Control" (new device-type concept, not
      yet in the type enum — treat as a UI mockup/future extension unless
      a new "tv" type is explicitly added to Device model + Firestore
      schema + FirestoreService).
    - Directional Pad (OK center).
    - Media Controls: Home, Settings, Back, Rewind, Play/Pause, Fast Forward.
    - Linear Volume Slider.

B. ALL DEVICES SCREEN
* Header: Back button, Title "All Devices", Status summary, Filter icon.
* Search: Large rounded "Search devices or rooms..." bar.
* Category Chips: All, Lights, HVAC, Sensors, Outlets — map to existing
  `type` field where possible (outlet, bulb, multiswitch, iron, camera);
  chips without a matching type (HVAC, Sensors) should be treated as
  future/placeholder categories unless new device types are added.
* Device List:
    - Vertical list of tiles, sourced across ALL floors (aggregate
      streamDevices across floors, or add a new
      streamAllDevices() method to FirestoreService).
    - Icon, Name, Location (Room - Floor) — Floor is available now via
      floorId -> floors/{floorId}.name; Room depends on the schema
      addition noted in Section 2A.
    - Real-time status badge (e.g., ON - Now) from `status`.
    - Power consumption badge (e.g., 120W) — NOTE: no existing field for
      this; treat as optional future metadata, do not block on it.
    - Trailing power toggle switch, wired to existing toggle methods.
* Add Device: Floating Action Button (+) at bottom-right — reuse/extend
  the existing add-device dialog pattern from FloorDetailScreen, but
  support all device types (currently only Outlet has an add-dialog).

C. ENERGY ANALYSIS SCREEN
* Header: "Energy Reports", Month selector, Export button.
* Usage Summary Cards:
    - "Today's Usage" (kWh + USD est).
    - "Monthly Total" (% change vs last month).
    - NOTE: usageLogs currently only records ON/OFF/AUTO_CUTOFF events
      with timestamps, not energy/kWh values. Either (a) derive an
      approximate usage estimate from ON-duration between paired ON/OFF
      log entries, or (b) treat kWh figures as illustrative/mocked until
      a real energy-metering field is added. Do not silently fabricate
      data in a way that misrepresents it as measured.
* Charts (Integration with fl_chart):
    - Usage Overview: Bar chart (Usage vs Day of Week).
    - Room Comparison: Donut chart with legend and percentages (depends
      on the room field discussed above).
* Top Consumers: List of devices with their specific kWh usage — same
  caveat as Usage Summary Cards above regarding data availability.
* Data source: build on top of existing streamUsageLogs(deviceId); may
  need a new aggregate query/service method for cross-device reporting
  rather than calling per-device streams individually.

D. SECURITY CAMERA SCREEN
* Live Feed: Large video player view.
    - Existing CameraDevice model only has `snapshotUrl` (a static
      image/mock), not a live stream URL. Per the original project spec,
      mock camera snapshots / mock URI streams are acceptable — treat
      "LIVE" as a simulated/mock state, not a real video feed, unless a
      streamUrl field is explicitly added to the schema.
* Controls:
    - "LIVE" status indicator.
    - PTZ Control Overlay (Directional pad) — mock/non-functional is
      acceptable per spec (mock camera system).
    - Action Buttons: Mic (Intercom), Camera (Snapshot), Fullscreen.
* Navigation: Chips for camera locations (Exterior, Ground Floor, etc.) —
  derive from floor names / room field where available.
* Camera Switcher: Horizontal scrollable thumbnails of all active
  cameras — query devices where type == "camera" across floors.

E. NOTIFICATIONS SCREEN
* Header: "Notifications" with count, "Mark all read" button.
    - Count and list sourced from streamAlerts(); "Mark all read" should
      batch-update `acknowledged: true` on alert documents (add a
      markAllAlertsRead() method to FirestoreService rather than looping
      writes directly in the widget).
* Filters: All, Unread, Critical.
    - Unread = acknowledged == false.
    - Critical: no existing severity field on /alerts — either add a
      `severity` field ("info" | "warning" | "critical") when alerts are
      created (e.g. AUTO_CUTOFF alerts should be "critical"), or treat
      all current alerts as one tier until this field exists.
* Notification Cards:
    - Severity coding (Red border = Critical, Yellow = Warning, Blue =
      Info) — depends on the severity field above.
    - Device/Event title, detailed description (from `message`), room
      location, timestamp (from `timestamp`).
    - Dismiss (X) button — should update/delete the alert doc via a new
      FirestoreService method (e.g. dismissAlert(alertId)), not a raw
      Firestore call from the widget.

3. FUNCTIONAL REQUIREMENTS
==================================================
* State Management: Real-time synchronization using Provider and
  Firestore. NOTE: `provider` package is already added as a dependency
  but not yet used anywhere in the app — current screens call
  FirestoreService directly via StreamBuilder. Introducing Provider
  should wrap/organize this existing stream-based approach (e.g. as a
  ChangeNotifierProvider exposing FirestoreService or view-models), not
  replace the underlying Firestore sync mechanism described in 0.6.
* Safety Logic: Auto-shutoff for safety-critical devices (e.g., Irons)
  with persistent timers. ALREADY IMPLEMENTED server-side via the
  checkSafetyCutoffs Cloud Function (see 0.7) — UI work here should focus
  on surfacing turnedOnAt / maxOnDurationMinutes as a live countdown on
  the Iron device card, not reimplementing the cutoff logic client-side.
* Scheduling: Capability to set Start/End times for lights/plugs. Bulb
  model already has scheduleStart/scheduleEnd fields — UI needs a
  time-picker to set these; the actual scheduled ON/OFF enforcement
  Cloud Function is still OUTSTANDING (see 0.9) and should follow the
  same onSchedule pattern as checkSafetyCutoffs.
* Navigation: Custom Persistent Bottom Nav with active state indicators
  (pill-shaped, per Section 1).
* Animations: Smooth transitions between screens and room detail panels.
