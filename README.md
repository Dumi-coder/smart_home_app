## Overview

This system lets a user manage multiple house floors, monitor and control heterogeneous smart devices (power outlets, multi-switch panels, safety-critical appliances like irons, schedulable lights, and mock security cameras), and see automated backend safety rules enforced in real time — without any manual refresh anywhere in the app.

A companion **Hardware Simulator** screen listens to the same live Firestore data and visually represents what the physical devices would be doing, standing in for real IoT hardware.

## Firestore Schema

```
/floors/{floorId}
    name: string
    gridWidth: number
    gridHeight: number
    imageUrl: string

/floors/{floorId}/rooms/{roomId}
    name: string

/floors/{floorId}/devices/{deviceId}
    type: "outlet" | "multiswitch" | "iron" | "bulb" | "camera"
    name: string
    x: number
    y: number
    status: "ON" | "OFF" | "ERROR" | "DISCONNECTED"
    room: string (optional)

    # multiswitch only
    switches: [ { id, label, state } ]

    # iron only (safety-critical)
    maxOnDurationMinutes: number
    turnedOnAt: timestamp | null

    # bulb only (scheduled)
    scheduleStart: string   # "HH:mm", e.g. "18:00"
    scheduleEnd: string     # "HH:mm", e.g. "23:00"

    # camera only
    snapshotUrl: string

/usageLogs/{logId}
    deviceId: string
    floorId: string
    event: "ON" | "OFF" | "AUTO_CUTOFF"
    timestamp: timestamp

/alerts/{alertId}
    title: string
    message: string
    severity: "critical" | "warning" | "info"
    room: string (optional)
    deviceId: string (optional)
    icon: string
    timestamp: timestamp
    acknowledged: boolean

/energyUsage/{readingId}
    date: timestamp
    room: string
    device: string
    kWh: number

/houseMembers/{memberId}
    name: string
    email: string
    role: "Owner" | "Admin" | "Guest"
    online: boolean
    avatarUrl: string (optional)

/scenes/{sceneId}
    name: string

/settings/preferences
    darkMode: boolean
    pushNotifications: boolean
    firebaseSync: boolean
```

## How to Run — Frontend (Flutter App)

### Prerequisites
- Flutter SDK (stable channel)
- Android Studio with the Flutter and Dart plugins
- A physical Android device (USB debugging enabled) or an Android emulator
- Node.js + npm (needed for the Firebase CLI, used in setup)

### Steps

```bash
# 1. Clone the repo
git clone https://github.com/Dumi-coder/smart_home_app.git
cd smart_home_app

# 2. Install Flutter dependencies
flutter pub get

# 3. Confirm your toolchain is healthy
flutter doctor
```

**Firebase connection:** `lib/firebase_options.dart` is already committed to this repo and points at the shared project (`smarthome-3508e`). You do **not** need to run `flutterfire configure` yourself — doing so risks creating a second, disconnected Firebase project. If this file is ever missing, run `flutterfire configure` and select the **existing** `SmartHome` project, never "create a new project."

```bash
# 4. Run the app
flutter run
```
Select a connected device or emulator when prompted, or use `flutter devices` to list options and `flutter run -d <device-id>` to target one directly.

### First-time data setup
The app includes a one-time **seed data** action (see `lib/services/seed_data.dart`) that populates every collection with realistic sample data — floors, rooms, all 5 device types, alerts, ~30 days of energy readings, house members, and scenes. Trigger it once from the app (cloud-upload icon in the relevant screen) after your first successful run. Avoid triggering it more than once, or you'll get duplicate floors/devices.

## How to Run — Backend (Cloud Functions)

The backend consists of two scheduled Cloud Functions, both already **deployed to production**:

- **`checkSafetyCutoffs`** — runs every 1 minute; force-flips any `iron` device to `OFF` if it has been on longer than its `maxOnDurationMinutes`, logs an `AUTO_CUTOFF` usage event and writes an alert.
- **`checkBulbSchedules`** — runs every 1 minute; compares the current time (explicitly computed in `Asia/Colombo` timezone via `Intl.DateTimeFormat`, not server local time) against each bulb's `scheduleStart`/`scheduleEnd` window and turns it `ON`/`OFF` accordingly, logging usage events and alerts.

### Local development / testing

```bash
cd functions
npm install
npm run build
```

Test locally using the Firebase Emulator Suite before deploying changes:
```bash
firebase emulators:start --only functions,firestore,pubsub
```
Open the Emulator UI at `http://127.0.0.1:4000` to inspect local Firestore data and function logs. Since scheduled functions don't auto-fire on a timer inside the emulator, trigger them manually:
```bash
curl -X POST http://127.0.0.1:5001/smarthome-3508e/us-central1/checkSafetyCutoffs
curl -X POST http://127.0.0.1:5001/smarthome-3508e/us-central1/checkBulbSchedules
```
(If the exact function name differs, e.g. with a `-0` suffix, the emulator's error response will state the correct name to use.)

### Deploying changes

```bash
firebase deploy --only functions
```

Requires the project to be on the **Blaze** billing plan (scheduled functions use Cloud Scheduler, which isn't available on the free Spark plan). At this project's usage volume — two functions running once a minute — real-world cost is effectively $0; Cloud Scheduler includes 3 free jobs and Cloud Functions includes 2 million free invocations/month.

Check live logs for a deployed function:
```bash
firebase functions:log --only checkSafetyCutoffs
firebase functions:log --only checkBulbSchedules
```

## Synchronization Mechanism

The app uses **Firestore's real-time listeners** (`snapshots()` streams) instead of polling or manual refresh:

- Every screen displaying live data wraps its UI in a `StreamBuilder` bound to a `FirestoreService` stream method.
- Any write — from the mobile app, the Firebase Console, another team member's device, or a Cloud Function — is pushed automatically to every listening client.
- This gives bidirectional sync with no manual refresh logic anywhere: a toggle in the app reflects instantly in Firestore, and any external change reflects back into the UI just as fast.
- Safety-critical and scheduled devices are additionally monitored server-side by the two deployed Cloud Functions described above, so automation continues to run even if no mobile client is currently open.

## Floor Representation

Each floor document stores an abstract `gridWidth` × `gridHeight` grid alongside an optional `imageUrl` for a real floor-plan image. Devices store an `(x, y)` position within that grid. The **Floor Plan screen** overlays this grid on the floor's image, rendering every room (including empty ones) and every device on that floor as a positioned, tappable marker — colored by live status and draggable to reposition, which persists back to Firestore.

## Hardware Simulator

A dedicated screen (`simulator_screen.dart`, reachable from the Home screen header) listens to the exact same Firestore collections the main app uses, and visually represents each device as if it were the physical appliance — glowing when `ON`, dimmed when `OFF`. Devices are grouped by floor, then by room, including a dedicated "Exterior" group for outdoor cameras that aren't tied to any real floor document. This stands in for physical IoT hardware per the project brief, and demonstrates the same bidirectional sync visually: toggling a device anywhere in the main app updates the simulator live, and vice versa.

## Security

Firestore access is governed by `firestore.rules` at the project root. The app does not use Firebase Authentication (a deliberate scope decision for this project), so rules are structured to restrict reads/writes to the known collections and expected fields this app actually uses, rather than leaving the database fully open. Cloud Functions use the Admin SDK, which bypasses client security rules by design, so both scheduled functions continue to operate normally regardless of these rules.

Deploy rules changes with:
```bash
firebase deploy --only firestore:rules
```
